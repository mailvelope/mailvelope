# Threat model

## What this project does and where untrusted input enters
Mailvelope is an OpenPGP browser extension for Chrome (MV3 service worker) and Firefox (MV3 event page). It adds encryption to webmail: it finds armored PGP blocks in web pages, decrypts and verifies them, and lets the user compose encrypted mail. The decrypt view, editor, password, key import, key generation and backup UIs are extension pages. They are either framed into the webmail page (decrypt view, client-API containers) or opened as extension popup windows (editor started from the webmail compose field, password and import dialogs), so the page cannot read them. Web apps on watchlist entries with the API flag can also call a JavaScript API (client-API). The flag is preset for GMX, WEB.DE, Posteo, mailbox.org, mail.de, freenet.de, Riseup and FP De-Mail (`src/res/defaults.json`); other sites get it after the user confirms the authorization prompt or enables it in the watchlist settings.

Assets: private keys and their passphrases, decrypted plaintext and drafts, the integrity of the keyrings (which key belongs to which address), signature verification results, and Gmail OAuth tokens. With the GnuPG backend also the integrity of the user's system GnuPG keyring, which other programs on the machine use.

We assume these adversaries:
- **Web pages**: any site the user visits controls its own DOM and JavaScript and can frame Mailvelope's web-accessible UI components. On sites where Mailvelope runs (watchlist entries) this includes the armored text shown, every frame Mailvelope injects into and, on sites with the API flag, every client-API call. The webmail provider is one such page.
- **Other extensions**: with host permissions on a page they have that page's power there, including over the page's network traffic. Mailvelope registers no `onConnectExternal` or `onMessageExternal` listeners, so a path where another extension reaches the background or a controller directly is a High isolation bypass.
- **Senders of crafted messages**: control everything inside a PGP message: packets, MIME structure, HTML, attachments, file names, embedded keys. A client-API page may relay their Autocrypt headers (processed only when Autocrypt is enabled, off by default).
- **Key sources**: verifying keyservers (keys.mailvelope.com, keys.openpgp.org). Unlike classic SKS keyservers, they publish a user ID only after its owner has confirmed the address by email. For keyserver and WKD results, Mailvelope keeps only the user ID that matches the queried address. Verification shows control of the mailbox at upload time and nothing more, so these servers, WKD hosts, Autocrypt headers and keys pasted or uploaded by the user may still return malicious or mismatching keys.
- **Network MITM**: can read and modify traffic that is not authenticated end to end.
- **Provider APIs**: Gmail API responses (message bodies, attachments, headers) are untrusted data.

Entry points:
- Page DOM text scanned by the content scripts (`src/content-scripts/main.js`, frame classes and provider modules such as Gmail and Outlook on the web in `src/content-scripts/`).
- client-API: `window.postMessage` from the page script `src/client-API/client-api.js` to the content script `src/content-scripts/clientAPI.js`, then to `src/controller/api.controller.js`, the container controllers and the sync handler (`src/controller/sync.controller.js`).
- Domain authorization: a navigation to `https://api.mailvelope.com/authorize-domain/` opens the prompt for the tab's site (`src/lib/inject.js`, `src/controller/authDomain.controller.js`).
- Port messaging into the background: `chrome.runtime.onConnect` in `src/controller/main.controller.js`. `src/controller/factory.js` creates controllers based on the port name `type-id`. Controller ids appear in iframe URLs in the page DOM, so they are known to the page. The UI components listed in `web_accessible_resources` (`src/chrome/manifest.json`, `src/firefox/manifest.json`) can be framed by any website.
- Message parsing: OpenPGP via `src/modules/pgpModel.js`, MIME via `src/modules/mime.js` and `src/lib/mail-reader.js`. HTML is sanitized with DOMPurify in `src/lib/offscreen/offscreen.js` (offscreen document in Chrome, event page in Firefox) and rendered in a sandboxed iframe without scripts (`src/components/decrypt-message/components/ContentSandbox.js`).
- Key import and discovery: `src/controller/import.controller.js`, `src/modules/keyRegistry.js` (verifying keyservers, `wkdLocate.js`, Autocrypt), editor recipient lookup, sender key discovery (`acquireSigningKeys` in `pgpModel.js`), key binding (`src/modules/keyBinding.js`), keyring sync.
- Gmail integration: `src/modules/gmail.js`, `src/controller/gmail*.controller.js`, `src/content-scripts/gmailIntegration.js`.
- Optional GnuPG backend: `src/modules/gnupg.js`, `KeyringGPG.js` and `KeyStoreGPG.js` talk to the user's installed `gpgme-json` over native messaging (`gpgmejs`, optional `nativeMessaging` permission). The GnuPG keyring is the user's system keyring. With `prefer_gnupg` (default on) it comes first for decrypt, verify, sign and the editor, also for client-API decrypt and sign when GnuPG holds the private key (`getPreferredKeyringQueue` in `src/modules/keyring.js`). Sender-controlled ciphertext and signatures are passed to GnuPG. Recipient lookup results and newer public keys from other Mailvelope keyrings (`syncPublicKeys`) are imported into it without asking. Private keys and passphrases stay with gpg-agent and pinentry; Mailvelope never reads them. In scope: what Mailvelope sends to `gpgme-json` and how it maps the results (`mapSignatures` in `gnupg.js`). GnuPG and gpgme themselves are not.

## Components that matter most / least
Most:
- The decrypt and verify path through to rendering in the extension frame: `pgpModel`, `mime.js`, sanitization, `src/components/decrypt-message/`.
- The page boundary: content scripts, client-API bridge and `ApiController`, iframe isolation.
- Port and controller gating: `factory.js`, `main.controller.js`, `sub.controller.js`.
- Key import, update and discovery: which key ends up bound to which address, which key is picked for an address (`getKeyByAddress`, `getKeyData` in `keyring.js`), and when the user is asked.
- Keyring, password cache and token storage: `src/modules/KeyStoreLocal.js`, `src/modules/pwdCache.js`, `src/lib/lib-mvelo.js`.
- The GnuPG bridge: signature mapping in `gnupg.js` and which keys reach the system keyring.

Less: options/settings UI that only shows the user's own data, styling, locales (`locales/`), build tooling (`config/`, `Gruntfile.js`, `.build-tools/`).

## How to exercise it
- The image has run `npm ci`, the dev build (`build/chrome`, `build/firefox`) and `npm run build:integration`. The tests do not need network; key lookups fail fast offline.
- `npm test` runs all unit and integration tests. Run a single file with `npm test -- test/unit/modules/pgpModel.test.js`. Use `--maxWorkers=2` on the 2-CPU box.
- Unit tests (`test/unit/`) run in jsdom with a mocked `chrome` API. Tests under `controller/`, `lib/` and `modules/` also get simulated service-worker globals (`test/unit/jest.setup.js`).
- Integration tests (`test/integration/`) run in headless Chrome via Puppeteer on a `file://` page (`test/integration/setup/test-page.html`). The page loads background, content-script and client-API code as one bundle with a mocked `chrome` API. The extension itself is not loaded, so origin isolation is not exercised. The bundle sets `__DEV_MODE__`, which turns on `file://` origin relaxations in `clientAPI.js` and `client-api.js`; these are active only in this bundle. `window.testHarness` (`test/integration/setup/test-harness.js`) creates keyrings, real controllers, port pairs and the client-API.
- Fixtures: test keys and Autocrypt headers in `test/fixtures/`. Armored test messages are inline in the test files, e.g. `test/integration/controller/decrypt.controller.test.js`.
- `test/legacy/` is a dead Karma suite and is not run.
- The image has no GnuPG or `gpgme-json`, and no test covers the GnuPG path; review it from the code.

## How you rate severity
Rate by the worst outcome shown. Critical and High assume an adversary from the list above and no user action beyond reading mail or visiting the page. Needing an extra confirmation, an unusual user action or a non-default setting lowers the rating one step. The GnuPG backend is a supported configuration; findings on it are not lowered for needing it.
- **Critical**: plaintext, private keys, passphrases, the backup code or OAuth tokens reach the host page, another origin or the network. Example: script execution in an extension frame through crafted message HTML, or a client-API call that returns any of these unencrypted.
- **High**: iframe or origin isolation bypass. Examples: a web page or content script drives an extension frame, or opens a controller it should not get (for example `AppController`); a client-API call takes effect for a site that is not authorized, or on another site's keyring. A bypass that exposes an asset from the Critical list is Critical.
- **High**: signature or sender spoofing. Examples: a message is shown as validly signed by a key that did not sign it or did not sign that content, or a signature is attributed to the wrong user ID or address.
- **Medium to high**: unauthorized key import. A key enters or replaces an entry in the keyring without the confirmation its path requires, or gets bound to an address it does not carry, in a user ID or in the key binding record. This is high if it makes the user encrypt to an attacker's key without noticing, or if the key lands in the GnuPG keyring, which other programs on the system use. The automatic imports listed under designed behaviour below are not unauthorized, whichever keyring they reach.
- **Low**: denial of service. Examples: crashing or hanging the background with crafted input, a UI freeze, filling storage.

## Anything to leave alone
- OpenPGP.js internals (npm `openpgp`): report those upstream. How Mailvelope calls OpenPGP.js and acts on its results is in scope.
- Browser, OS and hardware compromise, renderer exploits, malware with user privileges, physical access and side channels.
- What other extensions can do with browser-granted powers outside any extension's control: reading plaintext the user copies (`clipboardRead`), and screenshots of the visible tab (`tabs.captureVisibleTab`), including framed Mailvelope views.
- Metadata visible to the provider: subject, recipients, key IDs and message size.
- Designed behaviour of the client-API. An authorized page may use the main keyring or create its own keyring scoped to its watchlist entry. It may query which addresses have keys, which also triggers verifying keyserver and WKD lookups for unknown addresses. It may export the user's own public key and request public key imports, which the user confirms unless they only update a known key (see key import below). It may set the logo shown for its keyring. The page receives public keys, ciphertext, encrypted keyring sync messages, and the private key backup encrypted with the backup code.
- Designed behaviour of key import (trust on first use). For a recipient without a local key, the editor popup and the app's encrypt page look the address up (verifying keyservers, WKD, Autocrypt) and import the first key found without asking. When the GnuPG keyring is in use, the key goes there too. This is deliberate for usability. An address that already has a key is not looked up again. The client-API editor container and sender key discovery (while decrypting or verifying) ask before importing a new key, and the import dialog flags a possible key rotation when the sender already has another key. Updates to a known key that do not change its validity are applied without asking. Keyring sync imports the keys from a sync message signed with the user's own key without asking. A newer version of a public key in one Mailvelope keyring is copied into the keyring in use, the GnuPG keyring included. With GnuPG, a signature that GnuPG verifies but rates as marginally trusted is shown as valid, since Mailvelope trusts every key in its keyrings. Key binding (`src/modules/keyBinding.js`, on by default): per keyring and sender address, Mailvelope records the key that made the newest valid signature on a message from that address. When several keys carry the address, it encrypts to that key instead of the most recently modified one. Report these only if they cross a boundary in the severity list.
- Storage readable by Mailvelope's own code. Page scripts cannot read `chrome.storage.local` (keyrings, OAuth tokens), but Mailvelope's content scripts can. `chrome.storage.session` (password cache) is readable only by extension pages and the background. Report only a path that exposes this data to page scripts, another origin or the network.
- `test/legacy/`, dependency CVEs that have no path reachable from Mailvelope, and the Outlook API integration (not on this branch).
